# KnowledgeForge — From Document Sprawl to Verified Architectural Knowledge

## Problem

Every enterprise architect we have spoken to in the last twelve months tells us a variant of the same story. A new platform team is asked to "take over" a system originally built by a partner three years ago. They are handed a SharePoint folder with two hundred PDFs of varying age, accuracy, and provenance. They are pointed at fifty Git repositories, half abandoned, the rest still receiving commits from people who left the company. They are told that the official documentation is "in the wiki", but the wiki was last updated before the cloud migration and now contradicts the running infrastructure in subtle but important ways. There is no architecture diagram that an engineer trusts. There is no list of services that a security officer can audit against. There is no clean dependency graph that a change-management board can use to sign off on a decommission. Every question — "what depends on this database?", "where do we process European customer data?", "which service owns this Kafka topic?" — turns into a multi-week archaeology project.

The cost of this *context recovery* is enormous and almost never measured. A senior engineer joining such a team spends three to six months learning the system before they can change it safely. A vendor due-diligence process slips by a quarter while consultants reverse-engineer the data flows. A regulator asks a question and the answer takes a month because no one knows where the canonical truth lives. Multiply this by every transformation, every M&A, every reorg, every cloud migration. The labor cost alone runs into millions per system; the opportunity cost — slow decisions, blocked roadmaps, eroded confidence — is larger still.

Existing tooling does not solve this. Static data catalogs (Collibra, Dataplex, Atlan) require *someone* to populate them, and that someone is exactly the person who does not have time. Vector RAG over the document dump produces answers that sound right but are not auditable. Diagramming tools (LucidChart, Structurizr, ArchiMate modellers) require manual maintenance that no one performs. Code-graph tools see the code but not the documents; documentation tools see the documents but not the code. The customer ends up paying for three half-solutions and still does not have a single trustworthy answer to the question "what is this system?".

## Solution

KnowledgeForge is an open-source, GCP-native AgenticRAG platform that builds — automatically and continuously — a verified ArchiMate 3.2 knowledge graph from your existing documents and source code, and then exposes that graph through a multi-agent orchestrator that can answer architectural questions with cited sources and labelled confidence. You point it at a SharePoint folder and a list of repositories. It parses every PDF, DOCX, PPTX, source file, and IaC manifest. It chunks, embeds, and stores them in Cloud Spanner. It uses Gemini 2.5 with Controlled Generation to extract typed entities (`BusinessProcess`, `ApplicationComponent`, `DataObject`, `TechnologyService`, ...) and typed relationships (`realizes`, `uses`, `accesses`, `triggers`, ...) following the ArchiMate 3.2 standard. Every relationship is labelled with a confidence tier — `EXTRACTED` (literal in source), `INFERRED` (model-deduced), or `AMBIGUOUS` (model uncertain). Every entity is reconciled across documents through exact-name + vector-similarity matching, so "Claims Service", "Claims Management Platform", and "ClaimsAPI" collapse into a single graph node when they refer to the same thing.

Once the graph exists, the multi-agent retriever takes natural-language questions and *decides* how to answer them. Simple lookups go to vector search. Topology questions ("what depends on X?") go to graph traversal. Specific term searches go to keyword. Complex questions trigger all three in parallel, fuse the results with Reciprocal Rank Fusion, rerank with Vertex AI, and run a final verification pass that labels each claim `SUPPORTED`, `CONTRADICTED`, or `UNSUPPORTED` by the evidence. The user sees the answer, the cited chunks, the highlighted graph subgraph, and the confidence label — all in one streaming response. External agents talk to the same backend through the bundled MCP server, so a Claude Code or Cursor session in the engineer's IDE can query the corporate architecture without copy-paste.

## How it works

The ingestion pipeline is a five-stage flow. First, **parse**: PDF text and figures via LiteParse (PDFium + sharp), DOCX via Mammoth, PPTX via JSZip, source via tree-sitter. Each parser emits a normalized document model with page-level provenance. Second, **chunk**: semantic chunking targets ~500-token windows, attaches a Contextual Retrieval prefix (a model-generated sentence that situates the chunk in its document), and emits separate multimodal image chunks for figures. Third, **embed**: `gemini-embedding-2-preview` produces 768-dimensional vectors for both text and images. Fourth, **graph extract**: a Gemini 2.5 call with a Controlled Generation schema returns a JSON list of typed entities and relationships. The extractor receives the chunk plus its document-level neighbour summaries to reduce hallucinated edges. Fifth, **persist & reconcile**: Cloud Spanner stores chunks, vectors, entities, and edges. A reconciliation pass merges duplicate entities by exact-match then by cosine similarity above a tuned threshold.

The retrieval pipeline mirrors the ingestion in reverse. The orchestrator agent classifies the user's query into a retrieval plan (vector / graph / keyword / hybrid). For graph queries it issues GQL traversals against Spanner Graph; for vector it does cosine top-k; for keyword it uses Spanner full-text indexes. The candidate sets are merged with RRF, reranked by Vertex AI Reranker for relevance, then handed to the synthesis agent which composes the answer. A verification agent re-reads the answer claim-by-claim against the cited chunks and assigns the per-claim confidence label. The whole exchange streams back over AG-UI / SSE to the frontend, which highlights the subgraph in the live force-directed view.

## Differentiators vs Knowledge Catalog

Google Cloud Knowledge Catalog (Dataplex Universal Catalog) is excellent at one job: holding metadata for assets that already live in GCP. It indexes BigQuery tables, GCS buckets, Pub/Sub topics, Vertex AI models. It assumes the assets exist, are inside GCP, and that someone — a data steward — will write the descriptions. KnowledgeForge solves a different problem: the *pre-cloud* problem and the *cross-cloud* problem. Most enterprise architecture lives in legacy documents and on-prem code that Dataplex will never see. KnowledgeForge is designed to ingest exactly that material and to do so without asking a human to write descriptions.

Four concrete differentiators. **(1) Pre-cloud-aware**: KnowledgeForge ingests PDFs, DOCX, PPTX, runbooks, vendor contracts, and on-prem config files. It does not require the underlying asset to exist in any cloud. **(2) Code-aware via AST**: tree-sitter-based extraction reads Java, Python, Go, TypeScript, C#, and Terraform. Calls between services, Kafka topic publish/subscribe, IaC dependencies, and DB access patterns all become graph edges automatically. Dataplex sees none of this. **(3) Agentic verification with confidence labels**: every claim the agent makes is verified against the retrieved evidence and labelled `SUPPORTED` / `CONTRADICTED` / `UNSUPPORTED`. Every graph edge carries `EXTRACTED` / `INFERRED` / `AMBIGUOUS`. This is the auditability story regulators ask about; Dataplex offers no equivalent at the answer level. **(4) MCP-native**: the bundled MCP server makes the entire knowledge base directly addressable from any MCP-compatible AI client (Claude Code, Cursor, Continue). Engineers query the architecture from the same IDE where they write code, with no copy-paste.

These are not competitive claims. KnowledgeForge is designed to *complement* Knowledge Catalog: ingest the unstructured world into a graph, then sync the resulting structured entries into Dataplex as governed catalog entries (Milestone B). The customer keeps Dataplex as the system of record; KnowledgeForge becomes the upstream pipeline that finally populates it.

## Extension story

KnowledgeForge is built as an extensible pipeline, not a finished product. Three extension paths are already scoped. **(A) Knowledge Catalog sync** (Milestone B): a one-way sync that promotes graph entities into Dataplex Entries, with relationships encoded as Aspects. Demo'd in Scenario 3. The customer's enterprise catalog gets populated automatically from the same source documents that previously sat dormant in SharePoint. **(B) Telco SID overlay**: TM Forum's Information Framework (SID) describes telco-specific entity types (`Customer`, `Service`, `Resource`, `Product`) that map cleanly onto ArchiMate's Business and Application layers. A SID overlay swaps the Controlled Generation schema for the SID schema and produces a telco-native graph. The same retrieval and verification pipeline applies unchanged. **(C) Custom ontologies**: any customer with an internal taxonomy (a banking reference data model, a healthcare HL7 FHIR overlay, a manufacturing ISA-95) can swap the schema. The architecture cleanly separates the schema (data contract) from the pipeline (parser → chunker → embedder → extractor → reconciler) so swapping ontologies does not require a rewrite.

Distribution-wise, KnowledgeForge ships in three forms. The **web frontend** at `kb-frontend/` is the demo and analyst-facing surface. The **MCP server** at `kb-mcp-server/` is the developer-facing surface for IDE-embedded agents. The **HTTP API** at `kb-agent/` is the integration surface for downstream systems (data catalogs, ITSM, change-management boards). Multi-CLI distribution (Claude Code skill, Gemini CLI extension — see `gemini-extension.json` in repo root) is already in place; adding new CLIs is a config change, not a port. The customer chooses how their teams consume the knowledge.

## Proof points

The repository contains an automated three-layer evaluation harness (`evaluation/run_eval.py`): L1 graph construction quality, L2 retrieval quality (graph vs vector A/B), L3 answer quality (LLM-as-judge). The most recent L2 run, captured in `evaluation/results/eval_pro_l2.json`, reports the following on a 30-question ArchiSurance benchmark spanning single-hop, multi-hop, completeness, cross-document, entity-resolution, and graph-advantage categories:

```
avg_full_pipeline_recall:  0.347
avg_vector_only_recall:    0.736
avg_graph_uplift:         -0.389
avg_multihop_uplift:      -0.412
questions_where_graph_helps: 1 / 30
```
*(Source: `evaluation/results/eval_pro_l2.json` aggregates block.)*

We report this honestly: on the current benchmark, the full pipeline *underperforms* a vector-only baseline on average recall. This is exactly why we ship the evaluation harness with the product. The L2 result is telling us that the current graph-extraction quality is not yet good enough to consistently lift retrieval — a known issue we are addressing in Milestone C through schema-tightening and reconciliation improvements. The benchmark is run on every change. The number is the number. A vendor that hands you a glossy deck without the eval suite is hiding the same number; we publish it.

What works today, demonstrably: the L1 graph-construction pass extracts hundreds of typed entities per document with confidence labels, the verification layer reliably catches unsupported claims (Scenario 1, query 4), and the impact-analysis BFS (Scenario 2) is deterministic and auditable in a way no vector RAG can be.

Beyond the headline aggregates, the per-question breakdown in `eval_pro_l2.json` exposes where the pipeline does and does not earn its keep. Several `single_hop` questions show the graph retrieval injecting noise (e.g., `single_hop_1` records a graph_uplift of -0.667 because vector-only already retrieved the relevant chunk and the graph fan-out diluted the context window). The `cross_document` and `entity_resolution` categories — where graph topology should matter most — are the next optimization target. Because every question has a stable id and the harness writes a timestamped JSON file per run, before/after comparisons across schema and reconciliation changes are mechanical. We use the same harness to gate releases.

The product is honest about where it is — and the open eval harness is the contract that keeps it that way. A buyer can re-run the eval against their own corpus before signing anything; the harness is part of the repo, not a sales artifact.
